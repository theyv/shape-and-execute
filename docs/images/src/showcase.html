Finally, orchestration that ships. Not agentic theater.

A Claude Code and Codex workflow that gets the job done. Every time.

skill + sae (Python CLI) + local viewer · github.com/theyv/shape-and-execute

Why another orchestrator?

01

It scales with the task.

Big or small, one tool fits. The orchestrator adds, changes and cancels jobs as the work unfolds; a small task skips whole steps.

02

Human work first.

Design, decisions, tradeoffs: what even the best model cannot read from your head. Most of your time goes into shaping; planning and execution follow the spec.

03

No false ceremony.

It stays light: one command to remember, not dozens. No heavy workflow that burns tokens on ceremony without better results.

SHAPE1 / 7

Problem

Intent matures while coding

You know what you want only once changing course is expensive.

Fix

Grill before code

The agent asks rounds of questions, each with A/B/C answers and a recommendation. Then a second model can attack the spec in an adversarial review.

SHAPE2 / 7

Problem

The intent gets lost

Precise at the start of a chat, vague after compactions.

Fix

Two files, two jobs

intent.md keeps the why, in the owner's words. specs.md keeps the contract: requirements with IDs and acceptance checks. Rejected ideas stay in the chat. Every decision is tagged [human], [agent] or [joint].

PLAN3 / 7

Problem

Planning while coding

A model plans well and codes well, but when it does both at once, every switch blurs its attention mechanism.

Fix

Planning is its own step

A planner turns the spec into a job graph. Each job fits a fresh context, with its own checks. It starts with one worker and runs jobs in parallel only when that really saves time.

PLAN4 / 7

Problem

Orchestrators pick models badly

Left to the harness, orchestration is luck: it skips subagents or spawns too many, on the wrong model and effort. Too weak, and the work rests on bad assumptions; too strong, and the quota burns.

Fix

Economy, balanced, premium

Chosen in the plan: you set a level per phase, the planner sets a difficulty per job. Settings map each pair to an exact model and effort. Any job can be overridden; sae prints every dispatch.

EXECUTE5 / 7

Problem

Too big for one context

A big task overflows one context; each compaction blurs it.

Fix

One fresh worker per job

Each job starts in a fresh context. Parallel jobs get their own branch and worktree; sae merges them into one task branch. You keep working in the repo. Nothing is pushed; only you merge.

ALWAYS6 / 7

Problem

Resuming a session

After a /clear or a few compactions, the business problem is gone. Moving the task to another harness starts from zero too.

Fix

Files are the memory

Any session, any model, even the other harness, resumes from the task folder alone. sae, a Python CLI, writes all state, so bookkeeping costs no agent tokens.

ALWAYS7 / 7

Problem

Side fixes poison context

An agent stops to fix an unrelated bug on the side. The detour contaminates its context. The task rarely fails; it comes out worse, in ways you do not see but do feel.

Fix

Write it down, carry on

The agent files a finding and keeps working. Later, triage turns findings into tasks, backlog items or nothing; decision drafts become ADRs.

Put together

You stay in control: five interaction modes from full-auto to interactive, a next-step card before every bigger dispatch, and settings change only on your word.

Built on five assumptions

01

Decisions are yours.

Facts and implementation are the agents'. The task record keeps the tribal knowledge: why, what was rejected, who decided. What the code already shows stays out of commits and docs.

02

Quota is limited.

Not every step needs the biggest model.

03

A contract before code.

A spec checked early is cheaper than fixing several jobs. Every job carries its own verify commands, and sae re-runs them before the merge: done is checked, not claimed.

04

Files outlive chats.

The task record is committed with the code, like code. What is not written down is lost at the next compaction.

05

Light in its complexity.

Complex work, done with simple, smart parts: plain files, one small CLI, no MCP servers, no hooks. The viewer is an optional local page. The bookkeeping is the CLI's, not yours or an agent's.

The seven problems above follow from these.

Built on PROSE

PROSE is Daniel Meppiel's five constraints for agentic systems, from The Agentic SDLC Handbook, chapter 13. Every task you run gets all five; the skill's own files follow them too.
