# Intent: GitHub sync for backlog, tasks and pull requests

**Status: to be thought through and decided** before any spec. The owner is not sure yet which
option fits ("I have not decided yet."); this item lists every option so the owner can
decide consciously later.

## Problem

Tasks, the backlog, findings and results of shape-and-execute live only as Markdown files in
`.tasks/`. GitHub, where the code goes, knows nothing about them: backlog items are not issues,
a finished task is not a pull request, and nothing links the two. The owner wants the work to
be visible on GitHub too, without losing the simplicity of plain files in the repository.

## Goal

Decide how shape-and-execute and GitHub should relate, starting with the owner working alone,
with a clear view of what a team would need later.

- Owner's idea (2026-10-13): a backlog area folder (`.tasks/backlog/<area>/`, for example one per
  skill) becomes a GitHub issue label of the same name.

## Options for the owner working alone

1. **Mirror: Markdown files stay the source, GitHub mirrors them** (the owner's current
   leaning). Backlog items stay files in `.tasks/backlog/`, and each also exists as a GitHub
   issue; `sae finish` produces a pull request. The owner: "It may be simpler to keep Markdown files in the repository as they are now and mirror them on GitHub." Open: which side wins on a conflict (edit of the issue vs edit of the file), when
   sync runs (on every `sae` command, at finish, on demand), and whether closing an issue on
   GitHub closes the backlog item.
2. **Two-way sync of the backlog with issues.** An issue created on GitHub appears as a backlog
   item, and the other way round; picking up an item starts a task (`sae new --from-issue 123`).
   More convenient, harder to get right (conflicts, deleted issues, labels).
3. **One way, at the edges only.** Start a task from an issue; at finish, write the pull
   request description from the final report with "closes #123". The backlog stays files only.
   The smallest change.
4. **GitHub as the source.** The backlog lives as issues only; `.tasks/backlog/` disappears.
   Needs network and `gh` for every backlog operation; loses offline work and plain-file
   history.
5. **Pull requests at finish** (combinable with 1–3): `sae finish` opens a draft pull request
   through `gh`. This needs a push, which is a hard stop today: the owner would have to approve
   an explicit exception, per task or in the settings.

Also to decide: whether findings and decision-record drafts become issues too, or stay local
until triage.

## Options for a team (deferred for now, described for a later decision)

- **Claims and visibility through issues:** an issue's assignee shows who works on a task;
  tasks in progress are visible to everyone as issues or draft pull requests, not only as
  files on someone's branch.
- **A project board** (GitHub Projects) as the team's Kanban: backlog, shaping, executing,
  review, done, fed by the sync.
- **Pull request review as a gate:** the integration review or the owner's approval happens
  on the pull request, so teammates see and comment on it.
- **A team viewer as a separate service** tied to pull requests, as the parking lot already
  expects ([decision record](../../docs/adr/2026-10-10-cheap-decisions-that-keep-the-door-open.md)).

## Constraints

- Nothing pushes or changes GitHub without the owner's explicit approval (today's hard stop).
- Claude Code and Codex parity; `gh` is the expected tool.
- Plain files must keep working offline and without GitHub (other repositories, GitLab, no
  remote).
