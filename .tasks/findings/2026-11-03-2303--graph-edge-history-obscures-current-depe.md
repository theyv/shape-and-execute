# Graph edge history obscures current dependencies and makes repair hard

## Observation
During a live execution, the owner repeatedly asked the orchestrator to repair the dependency graph. The orchestrator could not reliably distinguish current scheduling edges, removed-edge history, and edges generated by review/final gates from the rendered graph. It first changed a local dependency, then removed redundant edges, before checking the requested invariant across the whole graph. Removing edges made the picture noisier because the viewer continued to draw them as dashed historical edges. Some product and integration jobs also had no dependency path to the packaging gate. Those were real topology gaps; the dashed paths were a different issue. The owner had to send several screenshots and restate the same requirement.

## Evidence

- `task-views.js:4-8` reconstructs added and removed edges from the event history. `task-views.js:250` draws removed edges in the main graph. A dependency repair therefore adds historical lines to the same view that the owner uses to inspect the current plan.
- The graph combines job dependencies, generated review edges, target/fix edges, collapsed review rows, historical edges and phase edges (`task-views.js`, `graph()`). A visual path is not enough to establish the current scheduling constraint.
- The orchestrator had to read `state.json` and write a temporary recursive reachability check to find the missing product/integration predecessors. `sae check` checks cycles, unknown dependencies and coverage, but cannot check an owner-specified invariant such as "every product job precedes the packaging job".
- The viewer reduces transitive generated edges into the Integration card (`task-views.js:245-247`), but removed edges are still drawn afterwards. Reducing current job dependencies alone does not produce a clean current-state view.
- `sae job edit` refuses a non-pending job (`planning.py:248`). A repair involving historical dependencies needs a separate diagnosis; the agent must not bypass this guard by editing state files.
- A later live change reproduced the problem with a newly added translation guard. The viewer did not make it obvious that the guard had no scheduling edge into the packaging gate. After the owner pointed it out, the orchestrator used `sae job edit ... --needs` as if it appended one predecessor. The command replaces the complete dependency list, so it temporarily reduced a package job with nineteen predecessors to only two. The CLI printed the replacement and the orchestrator restored the full list immediately, before any downstream dispatch, but the safe operation required copying the old list from terminal output.

## Cost

Several correction rounds and repeated owner screenshots during active execution. The orchestrator read the scheduler, CLI guards and viewer implementation, then used ad hoc scripts to check reachability. Its first cleanup increased visual noise and did not address all missing paths. No precise token or time total was measured.

The later reproduction added another owner screenshot and two graph edits for one intended edge: the mistaken full replacement, then restoration of every prior dependency plus the new one. No downstream job ran while the list was incomplete.

## Suggestion

- Provide a current-dependencies view by default, with removed edges and removed jobs available through an explicit history toggle. Keep all events in the audit history.
- Let an agent query direct and transitive predecessors/successors through the CLI, with the edge type and a concrete path. Add a check for a named gate: list jobs that have no path to it, with explicit exclusions.
- Show a graph-edit preview that distinguishes a scheduling change from a display-only reduction. Report which reachability constraints change before applying the edit.
- Make dependency mutation explicit: provide additive and subtractive forms such as `--add-needs` and `--remove-needs`, or require a clearly named `--replace-needs` for full replacement. A one-edge change should not require callers to reconstruct and resubmit the entire predecessor list.
- Test this with a large task containing nested fixes, multiple review rounds, removed edges and a packaging/deployment chain. Both the owner and an agent should be able to identify the same live blockers without reading viewer code.

These are improvement proposals, not permission to change a task's dependency semantics or bypass its review gates.
